The idea

Agree on what to build before anything gets built

With an AI agent, writing code is fast. Agreeing on what the code should do is the slow, valuable part. SDD makes that agreement a written, approved artefact the agent must follow.

StepWhat happensWho leads
specifyDescribe what users can do and see. No technology, no "how".FEH, with the agent drafting
clarifyThe agent lists what is missing or ambiguous. The business answers.FEH
G1The spec is approved in writing.FEH product owner

tasks → implement → convergeThe agent breaks the plan into tasks, builds them, then checks the result against the spec.VISEO, with FEH watching

The one ruleA change goes into the spec first, then the code. Never the other way round.

For facilitators and every pair

Every pair ends with the same app

An AI agent never writes identical code twice, so "the same result" means the same behaviour: same specs, same decisions, same data, same screens, and the same acceptance tests passing. Five controls make that happen.

Day 1 · 9:45

Anatomy of Spec Kit

Spec Kit is GitHub's open-source toolkit for Spec-Driven Development. It has two halves: a command-line tool that sets a project up once, and a set of slash commands the AI agent runs inside that project.

Part 1 The specify CLI · you run it in a terminal

It installs the templates, scripts and slash commands into a repo. You use it once per project (specify init), plus specify check to verify tools. It never writes a spec itself, despite the name.

Part 2 The slash commands · you run them inside your AI agent

Each command is a prompt file the agent follows. Each one reads what the previous step produced and writes the next document.

Day 1 · 10:30

Agree the constitution

The constitution is the set of rules every spec, plan and line of code must obey. This is a starting draft: read it with FEH, change anything that doesn't fit, then paste it.

/speckit.constitution

This project is a proof-of-concept web application for Far East
Hospitality (FEH), built with Spec-Driven Development during a two-day
workshop. Specifications approved by FEH define what the application
must do; the code is the evidence that it does it.

Principles:

1. Specification First. No code without an approved specification.
   Every acceptance criterion has an ID of the form AC-<spec>-<nn> and
   describes behaviour a user can observe. Specifications contain no
   technology choices.

2. Small Slices. Each specification is one feature that can be built,
   demonstrated and accepted on its own. A specification too big to
   build in half a day is split before it is approved.

3. Proven by Tests. Every acceptance criterion has at least one
   automated test whose name contains its ID. A feature is not done
   until all its tests pass.

4. Guest First. The application is used in a desktop web browser.
   Guest screens use plain language and meet basic accessibility
   (labels, contrast, keyboard use).

5. Synthetic Data Only. The application uses invented guests, rooms and
   properties. No real guest, staff or booking data, no real
   credentials, and nothing that would fall under PDPA.

6. Keep It Simple. One backend, one frontend, one local database, no
   paid or external services. Anything not needed by an approved acceptance
   criterion is not built.

7. Change Through the Spec. When behaviour needs to change, the
   specification is amended and re-approved first, then the code.
   Code that does something no specification asks for is a defect.

8. Stop and Report. After implementing a specification, the agent stops
   and reports what was built, the test results, and any acceptance
   criterion it could not satisfy. It never starts the next
   specification unprompted.

Governance: three gates per specification. G1 approves the
specification and is signed by the FEH product owner. G2 approves the
plan and is signed by the VISEO technical lead. G3 accepts the working
feature and is signed by both. Gates are recorded in
specs/<spec>/gates/ and never approved retroactively.

The facilitator pastes it once on the big screen, with the room's changes, and tags checkpoint/constitution. Pairs then sync:

git add -A && git commit -qm "my attempt"; git branch -f attempt/constitution
git fetch origin --tags
git reset --hard checkpoint/constitution
Talking point for FEHPrinciples 1, 5 and 7 are the ones a business owner cares about most: nothing is built that you didn't approve, no real guest data, and changes go through you.

Day 1 · 1:00 · before running spec 001

Deep dive: /speckit.specify

Turns a plain-language feature description into a structured specification. Your description is the most important input of the whole workshop: everything downstream is built from it.

What you give it

WhoThe person using the feature, and where. "A guest staying at an FEH serviced residence."
What and whyWhat they can do and see, and why it matters. "Ask for a service without calling the front desk."
LimitsWhat is rejected, who can't see it, what's out of scope.
Good input · what and whyPoor input · how
"The guest chooses what kind of help they need: housekeeping, maintenance, amenities or other.""Add a dropdown with four options that saves to the requests table."
"A request with no description is not accepted, and the guest is told what is missing.""Validate with Zod and return a 400."
"Staff only ever see requests for their own property.""Filter the SQL query by property_id."

What the agent does in order

  1. Picks a short name and the next number, then runs a script that creates a branch and a folder: 001-guest-service-request.
  2. Copies spec-template.md into the folder as spec.md.
  3. Fills it from your description, checking it against the constitution.
  4. Where something important is missing, makes a reasonable assumption and records it, or adds a [NEEDS CLARIFICATION] marker if it matters too much to guess (current versions allow only a few).
  5. Writes a quality checklist in checklists/requirements.md and checks the spec against it.
  6. Reports the branch, the file and whether the spec is ready for clarify.

Day 1 · 2:00

Deep dive: /speckit.clarify

Finds what the spec leaves open and asks you. It's the step where the business makes decisions, and the step most often skipped. Skipping it means the agent decides instead.

How it works

  1. The agent scans spec.md for gaps across a fixed set of areas: scope, users and roles, data, the user journey, error and edge cases, non-functional needs, constraints, and terms that are used loosely.
  2. It ranks the gaps by impact and asks the most important ones, one question at a time (five at most in current versions).
  3. Each question comes with options and a recommended answer. You can accept it, pick another, or give your own short answer.
  4. After each answer it updates the spec straight away: a Clarifications section records the question and answer, and the affected requirements and scenarios are rewritten.

What it looks like

Agent:  Question 1 of 5. How should a guest prove which stay a request
        belongs to?
        A  Room number and last name (recommended: no account needed)
        B  Booking reference
        C  One-time code sent by SMS
You:    A

Written into spec.md:
## Clarifications
### Session <date>
- Q: How does a guest identify their stay?
  A: Room number and last name, matched against a current stay.

Who answers

Kind of questionWho answersExample
Business ruleFEHCan a guest cancel a request?
Policy or riskFEHIs room number and last name secure enough?
Feasibility or costVISEO devCan we send SMS in a two-day proof of concept?
Nobody in the room knowsNobody guessesDeferred, and listed in the G1 record

Then our review prompt

Built-in clarify asks only a handful of questions. Our then sweeps the whole spec for anything else that's missing. Use both, in that order.

Run /speckit.clarify first, then paste this. The agent produces questions; the FEH product owner answers them.

Review the specification and identify:
- Missing requirements
- Ambiguous wording
- Business assumptions stated as fact
- Missing validation rules
- Edge cases
- Missing error handling
- Missing non-functional requirements

3 · Plan End of Day 1

/speckit.plan

Stack: a Django backend with Django REST Framework, and a React
frontend built with Vite and TypeScript. SQLite is the database.
Everything runs locally; no external services.

Repository layout:
- backend/   Django project; Python dependencies managed with uv
- frontend/  React app
- e2e/       Playwright tests (TypeScript) for user journeys

The frontend talks to the backend only through a JSON API under /api/.
In development the Vite server proxies /api to Django, so the browser
sees a single origin.

Authentication uses JSON Web Tokens with djangorestframework-simplejwt.
A guest who identifies their stay receives an access token scoped to
that stay only; it expires after 8 hours. The frontend keeps the token
in sessionStorage and sends it as "Authorization: Bearer <token>" on
every API call. A missing, expired or wrong-stay token gets a 401 or
403, and the screens send the guest back to "Identify your stay".

Seed data, screen layout, exact labels and colours come from
docs/reference.md, and the target screens are the images in
docs/mockup/; follow both exactly. Provide a management command,
seed_demo, that clears the database and loads that seed data.

All screens are designed for a desktop browser. Every rule is
validated in the API as well as in the form, and the screens show the
API's error messages.

Testing: pytest with pytest-django for business rules and the API;
Vitest with React Testing Library for screen behaviour; Playwright for
the guest journey. Every test name contains the acceptance criterion
ID it proves.

Commands, documented in the README:
- backend:  uv run python manage.py migrate · uv run python manage.py
            seed_demo · uv run python manage.py runserver · uv run pytest
- frontend: npm run dev · npm test
- e2e:      npx playwright test

Write the API contract (contracts/) and the data model
(data-model.md) first: the frontend is built against the contract
before the backend exists. Build order is scaffold, UI on mock data,
API endpoints, connect, integration tests, end-to-end tests.

Structure the data model and API so staff handling (spec 002) and
status tracking (spec 003) can be added without reworking them.
