The idea

Agree on what to build before anything gets built

With an AI agent, writing code is fast. Agreeing on what the code should do is the slow, valuable part. SDD makes that agreement a written, approved artefact the agent must follow.

StepWhat happensWho leads
specifyDescribe what users can do and see. No technology, no "how".FEH, with the agent drafting
clarifyThe agent lists what is missing or ambiguous. The business answers.FEH
G1The spec is approved in writing.FEH product owner
planDecide how: screens, data, stack, tests.VISEO
G2The plan is approved.VISEO tech lead
tasks → implement → convergeThe agent breaks the plan into tasks, builds them, then checks the result against the spec.VISEO, with FEH watching

The one ruleA change goes into the spec first, then the code. Never the other way round.

For facilitators and every participant

Every participant ends with the same app

An AI agent never writes identical code twice, so "the same result" means the same behaviour: same specs, same decisions, same data, same screens, and the same acceptance tests passing. Five controls make that happen.

ControlHow it works
1 · One run sheetEveryone sets up the project the same way (Step 1) and pastes the same blocks in the same order: constitution, then specs 001 to 005 in order. docs/reference.md fixes the seed data, screen labels and colours.
2 · Decisions made onceClarify questions are answered by FEH once, for the whole room. The facilitator types each answer on the big screen and everyone gives Copilot the same answer.
3 · Converge at every gateParticipants practise specify, clarify and plan themselves, then match the room's approved version on the big screen before moving on.
4 · Tests named after the criteriaEvery acceptance criterion in the approved spec gets a test with its ID in the name. At G3, everyone's build must pass a test for every criterion.
5 · Same toolsSame Spec Kit version and GitHub Copilot in Agent mode, checked in Step 0. Node 22+ and Python 3.12+.

Falling behind is fine

Nobody needs Git skills to catch up. At each gate the facilitator approves one version on the big screen and posts the approved file in the Teams chat. Anyone who is behind, or whose version drifted, pastes it in with the "catch up" prompt on that slide and carries on from the same place as everyone else.

If FEH decides differently in the roomThe facilitator updates the agreed answers on screen, re-runs that step once, and posts the new approved file. Everyone's own attempt stays in their Git history.

Anatomy of Spec Kit

Spec Kit is GitHub's open-source toolkit for Spec-Driven Development. It has two halves: a command-line tool that sets a project up once, and a set of skills GitHub Copilot runs inside that project.

Part 1 The specify CLI · you run it in a terminal

It installs the templates, scripts and Copilot skills into a repo. You use it once per project (specify init), plus specify check to verify tools. It never writes a spec itself, despite the name.

Part 2 The skills · you run them in Copilot Chat

Each skill is a SKILL.md prompt file Copilot follows when you type its name in chat, like /speckit-specify. Each one reads what the previous step produced and writes the next document.

Day 1 · 10:30 · how VISEO does it

How we build a constitution

On every spec-driven project we run, the constitution is the contract every spec, plan, task and line of code is checked against. It always has the same five parts, and every rule in it can be failed in a review.

PartWhat goes inWhy
Core PrinciplesNumbered rules (I, II, III…), each with a short title, MUST / MUST NOT statements, and a RationalePlans and reviews cite them by number: "this task violates Principle II"
Technology StandardsThe fixed stack, test tools, and the visual design tokens, each colour with a meaningCopilot stops choosing technology; every plan starts from the same decisions
Development Workflowspecify → clarify G1 → plan → tasks → analyze G2 → implement → converge G3 → commitEveryone knows who decides at each gate
Definition of DoneA checklist a spec must pass: approved, tests pass, traceability confirmed, shown on screen, committed"Done" is never a matter of opinion
GovernanceHow it changes: a stated reason, a semantic version bump, sign-off, a version lineChanging the rules is visible and deliberate

What makes a good principle

  • It can be failed. Written with MUST, MUST NOT or SHALL. "Be secure" is a wish; "a person MUST only see their own hotel's data" is a rule.
  • It says why. Every principle ends with a Rationale, citing the client's requirement ID where there is one (FEH NFR-001).
  • It's specific to this project. The client's hard constraints become principles; generic good advice doesn't.
  • It's enforceable in one place. "Isolation enforced in one place" gives the plan something concrete to design.
  • There are few enough to remember. If a principle never changes a decision, cut it.

Where principles come from patterns from our past projects

SourcePattern we've usedIn this project
The client's hard constraintsA travel agent: "every fact MUST trace to an API response". An on-prem imaging kiosk: "zero network calls at runtime", "detect, don't alter".Hotel isolation · nothing disappears · synthetic data only
How we deliver, on every projectTraceability (every criterion → a test) · test-first · single capability (one spec, one commit) · AI under human review · stop and report · change through the specThe same, unchanged
The time boxScope freeze on a date · completeness before polish · demonstrability ("every spec states what it looks like on screen")Keep it small · demonstrability
The testRead a principle and ask: could a reviewer reject a pull request because of it? If not, rewrite it or remove it.

# Meeting Action Tracker Constitution

Workshop MVP for Far East Hospitality (FEH), built with Spec-Driven
Development during the two-day session, 15–16 October 2026. One
constitution for both workshop tracks: MVP 1 (voice capture) and MVP 2
(meeting action tracker). What each track builds is in its run sheet,
docs/specs.md.
Source requirements: FEH "Meeting Action Tracker: Requirements",
13 Oct 2026. Data, labels and look: docs/reference.md.

## Core Principles

### I. Specification First

No code MUST be written without an approved specification.
Every acceptance criterion MUST have an ID of the form AC-<spec>-<nn> and
MUST describe behaviour a user can observe.
Specifications MUST NOT contain technology choices.

**Rationale**: FEH approves what is built before it is built. A
specification that names tables or frameworks hides the business decision
behind a technical one.

### II. Hotel Isolation

All meetings and action items MUST belong to exactly one hotel.
A person MUST only see and change data of the hotel they belong to.
Isolation MUST be enforced in one place, so no page, form or query can
return another hotel's data. Another hotel's data MUST behave as if it
does not exist.

**Rationale**: FEH NFR-001. Each property's data is separate; one
leaking query would break that promise for every hotel.

### III. Nothing Disappears

Action items MUST NOT be deleted; they are cancelled.
Every change to a meeting or an action item MUST be recorded with who,
when, the old value and the new value, from the first model onwards.
The record of changes MUST NOT be editable by users.

**Rationale**: FEH FR-014 and NFR-002. Any member can edit any item, so
the change record is the safeguard that makes open editing safe.

### IV. Synthetic Data Only

All hotels, people and actions MUST come from docs/reference.md.
No real FEH data, rates, forecasts or credentials MUST be used.

**Rationale**: The workshop runs on laptops outside FEH's environment.
Rate and forecast data is commercially sensitive even when invented.

### V. End-to-End Traceability

Every requirement MUST have acceptance criteria.
Every acceptance criterion MUST map to one or more automated tests whose
name contains its ID.
Traceability, not coverage percentage, is the test-sufficiency gate.

**Rationale**: At the demo FEH can point at any screen and ask "which
requirement is this, and what proves it?". The answer must be one click
away.

### VI. Test-First Development

Within each task, tests MUST be written before the code that satisfies
them, and MUST be seen to fail first.
Red → Green → Refactor.

**Rationale**: Tests written after the code tend to describe the code,
not the requirement.

### VII. Testing Pyramid

Most tests MUST be fast unit and integration tests (pytest).
End-to-end browser tests (Playwright) MUST be reserved for the main
meeting journey.

**Rationale**: Fast feedback during a one-day build; full-stack
confidence only where FEH will look.

### VIII. AI-Assisted Development Under Human Review

GitHub Copilot MAY generate specifications, plans, tasks and code.
A person MUST review every result before it is committed.
No task SHALL be phrased as "build the application".

**Rationale**: The agent is fast and confident, and sometimes wrong.
Review is where the participant adds value.

### IX. Single Capability Principle

Each specification, task and commit MUST deliver exactly one
demonstrable capability.
One spec = one commit = one capability on screen.

**Rationale**: Small capabilities can be approved, built, demonstrated
and rolled back one at a time, which is what lets the workshop stop at
any spec and still have something working.

### X. Built Through Spec Kit and GitHub Copilot

Every file MUST be produced through the Spec Kit cycle in GitHub Copilot
Agent mode.
Hand-written patches around the cycle are not permitted; if something is
wrong, the spec, plan or task is corrected and the agent re-runs it.

**Rationale**: The workshop is about the process. Hand fixes hide where
the specification was unclear.

### XI. Keep It Small

Only what an approved acceptance criterion asks for MUST be built. The
scope of each track is the approved specifications in its run sheet.
Microsoft Entra ID, emails, export, Teams transcripts, Databricks and
Azure hosting are out of scope for both tracks and MUST NOT be started.

**Rationale**: FEH's full requirements do not fit in two days. Each MVP
is chosen so it can be finished.

### XII. Change Through the Spec

When behaviour needs to change, the specification MUST be amended and
re-approved first, then the plan, tasks and code.
Code that does something no specification asks for is a defect.

**Rationale**: FEH stays in control of what the tracker does, even
mid-build.

### XIII. Stop and Report

After implementing a specification, the agent MUST stop and report what
was built, the test results, and any acceptance criterion it could not
satisfy.
It MUST NOT start the next specification unprompted.

**Rationale**: Each gate is a human decision.

### XIV. Demonstrability

Every specification MUST state what it looks like on screen.
A capability that cannot be shown in the final demo earns nothing.

**Rationale**: FEH judges the workshop by what it sees working.

### XV. AI Proposes, a Person Confirms

Anything an AI service produces in the app (a transcript, an extracted
action item) MUST be saved as Proposed and shown to a person.
Only a person MUST be able to confirm it; nothing becomes Confirmed
without that action.
The app MUST say which items came from AI until they are confirmed.

**Rationale**: AI extraction is fast and usually right, and sometimes
confidently wrong. The chair stays accountable for every action the
meeting records. Applies wherever the app calls an AI service.

### XVI. Secrets Stay Out of the Code

Keys and endpoints MUST only be read from environment variables (a
.env file that is listed in .gitignore).
Keys MUST NOT be committed, written in a spec, pasted in a chat, or
shown on screen.
The app MUST run, and every test MUST pass, with no keys at all.

**Rationale**: A leaked key is a security incident and a bill. A
workshop app that only runs with keys cannot be demonstrated when the
network or the key fails.
